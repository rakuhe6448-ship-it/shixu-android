# 1.2.1 手机闹钟

## 行为

- AI 的 `SET_ALARM` 操作产生独立手机闹钟卡片，不创建 Room 事项、提醒或任务草稿。模型误把明确的设闹钟请求返回为事项时，程序拒绝保存。
- 点击“确认并打开手机时钟”，使用 Android `AlarmClock.ACTION_SET_ALARM`，填写小时、分钟、名称、每周重复日，保留系统时钟界面供用户核对。声明 `com.android.alarm.permission.SET_ALARM`。
- 时间不明确先询问。待确认闹钟可引用补充；引用原始消息也可定位对应卡片。旧卡片替换后不可提交。
- 系统 Clock 没有返回正式闹钟 ID 或最终创建结果的通用机制，聊天仅记录“已交给手机时钟”。已交接闹钟的修改/删除须在手机时钟进行，不能用另建闹钟冒充修改。
- 单次日期必须是该时刻的下一次出现，确认时再次校验，防止过期卡片或任意未来日期变成提前响铃。每周重复按 ISO 星期转换为 `Calendar` 星期值。
- 无时钟应用或系统拒绝时保留未提交状态并报错。备份恢复后未提交闹钟卡片失效，不重放系统操作。数据库版本仍为 2，不修改现有事项与本地提醒的存储结构和调度算法。

## 本次验证

- `testDebugUnitTest`：53 个用例，0 失败、0 错误（其中 6 个为新增手机闹钟校验）。
- Android 15 / API 35 模拟器：13 个定向用例通过，包含 5 个手机闹钟集成用例、6 个原有多轮草稿用例、1 个闹钟备份恢复用例，以及 1 个 Compose 实际点击卡片并交给系统时钟的用例。
- 最终 APK 覆盖安装后，6 个手机闹钟与界面交接用例通过。系统前台为 `com.android.deskclock/.DeskClock`，实际显示 07:31、“时序联调测试”，启用开关为开启。
- 通过 `adb install -r` 覆盖安装，签名验证成功。
- 未调用收费模型 API；自然语言到 JSON 的模型表现仍取决于用户选择的兼容服务。测试覆盖结构校验、真实 Room 写入/隔离与系统时钟交接，不把模拟器结果当作 vivo 真机兼容验证。

## 手机验证

1. 覆盖安装 1.2.1，保留原有数据与 Key。
2. 在 AI 聊天发送“每天早上 7 点设一个起床闹钟”。核对手机闹钟卡片，点击“确认并打开手机时钟”，查看 07:00、每天重复、名称和启用状态。
3. 返回应用，确认排期和提醒列表没有多出名为“闹钟”的事项。
4. 在尚未交接的卡片上引用回复“改成 7 点半”，确认最新卡片显示 07:30，旧卡片不能提交。
5. 已交接的闹钟请从卡片“打开手机时钟”修改或关闭；测试后在时钟删除测试闹钟。

接口依据：[Android 官方 Clock intents](https://developer.android.com/guide/components/intents-common#Clock)、[AlarmClock API](https://developer.android.com/reference/android/provider/AlarmClock)。
