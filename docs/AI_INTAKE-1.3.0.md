# 1.3.0：追问草稿与提醒意图

## 数据与提交边界

Room schema 保持 2。`workingJson.formatVersion` 写入 2，同时读取原有 1；正式事项、提醒表和版本校验接口保持兼容。

在原有草稿 JSON 上新增：

- `groupId`：程序使用首次录入消息 ID。同一条消息拆出的草稿共享组标识，后续修订保持不变。仅在最近交互已有明确关联时，恢复同组尚未完成草稿作为候选；不会把所有历史草稿加入上下文。
- `questions`：每个事项各自的待补充问题，字段为 `TITLE / DATE / REPEAT / REMINDER_TIME / DETAILS`，附问题文本及可选的原始要求 `requestedValue`。保留未知需求，不能把不支持的周期伪装成已支持的正式规则。
- `reminderIntent`：兼容旧 `UNSPECIFIED / EXPLICIT`，新增 `NONE / NOTIFICATION / DEFAULT`。

状态由持久化内容计算：问题未解决、必需日期/标题缺失或明确需要通知却没有通知定义时，显示 `WAITING_INPUT`。符合完整规则后才显示 `PENDING`；提交时再读取数据库草稿检查完整性与 revision、正式任务 version。单纯改 UI 状态不能绕过待补充检查。

AI 可以同时返回 PATCH 草稿与 clarification，但不能在追问时混入 COMPLETE / DELETE。草稿保存不写正式事项/提醒表，不安排 AlarmManager。问题的清除必须对应实际字段补充；空 questions 不能抹掉尚未回答的重复方式等问题。

## 意图与重复

- 新事项没有通知要求：保存安排/待办，不自动附加通知。
- `reminderPolicy=NONE`：移除该事项全部通知及提醒时间问题，与添加通知同时出现时拒绝。已有事项通过原有事务保存和 `afterChange` 对账取消系统提醒。
- `NOTIFICATION`：用户明确要求通知。没有具体提醒定义时继续询问，不默认猜时刻。
- `DEFAULT`：用户明确选择默认截止提醒，尝试截止前一天 09:00；没有合适的未来时间时仍待补充。
- 每日/每周等无提醒重复待办仍需一个执行日期。没有指定首次日期且没有待确定的日期问题时，采用今天，时间保留为空。确认卡片显示实际日期；通知时刻不是保存该待办的必要条件。
- 当前能力仍为 NONE / DAILY / WEEKLY / MONTHLY / YEARLY，由程序在请求中提供完整列表。“每 N 天”保存为待确认问题，不推荐未实现的替代能力。

## 上下文与卡片

当前消息、最新相关草稿/正式事项、各自的问题和提醒意图、最多 6 条相关消息组成上下文；每条历史文字与分享文字各限制为 1000 字。不无限携带历史。

多个候选可以按明确名称、周期描述、待回答问题分别修改。根级 `clarificationTargets` 仅允许当前请求提供的短引用；真正操作的 target 仍由程序校验范围。目标含糊时继续追问。

没有关联 ID 的旧追问可以沿最多 16 跳引用链读取原始文字供重新解析；由显式引用恢复出的草稿关联回该引用节点及其直接用户来源。没有提供的正式任务 ID 仍不可操作。取消、冲突及过期版本不能通过该路径绕过。

卡片展示各自待补充问题和“不设置提醒／通知待补充”。批次中已完整的草稿可通过“单独核对这件事”复用原有单草稿预览和提交，不另造部分批次提交机制。

备份支持两种草稿格式，校验问题、意图和组来源；恢复后的旧待确认卡片继续失效，草稿需重新核对，恢复本身不创建提醒。

## 月历

月历网格识别横向拖动，超过 56dp 才切月；左右箭头复用同一日期切换方法。选中日期保留日号，超过目标月份天数时截到月末。竖向滚动及日期/事项点击保留。
